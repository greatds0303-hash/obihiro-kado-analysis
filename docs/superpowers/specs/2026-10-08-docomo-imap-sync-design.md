# EAGLE 帯広店 稼働分析 — docomoメール連携設計

## 目的と現状
稼働報告メールから来店客数、稼働率、客数シェアを集計し、Android向けPWAを開くだけで最新の11時・15時・19時のデータを閲覧できるようにする。
ユーザー提供の既存PWAを維持し、VMG履歴取込とIMAP自動同期を共存させる。
提供ZIPを確認済み。既存PWAはindex.html、manifest.webmanifest、service-worker.jsと3枚のアイコンからなる。VMGはVMSG内のbase64本文をcharset指定で復号し、IndexedDBのobihiro-kado-db/state/mainへ保存する。
既存のrecords/summaries/specialsとmailKeysの保存形式、CSV・JSONバックアップ／復元を維持する。配備オリジンが変わると既存IndexedDBは共有されないため、移行は既存JSONバックアップ／復元を利用する。

## 構成
既存PWA → 同一オリジンのExpress API → 同期サービス → imapflow／mailparser → SQLite。
DB操作をリポジトリ層に分離し、将来のPostgreSQL移行に備える。解析器はネットワークとDBから独立した純粋な処理とする。
フロントからIMAPには接続しない。APIはメール本文・認証情報を返さず、集計済みデータを提供する。

## 認証・配備
docomoのIMAP専用IDとパスワードはサーバー側.envのみで扱う。
imap.spmode.ne.jp:993へのTLS検証付き接続を使用する。.env.exampleは変数名と非秘密の既定値のみ記載する。
.env、node_modules、DB本体・WAL等の生成物をGitから除外する。ログとエラーは認証情報を除去する。
同一オリジンを既定とし、任意のCORSを許可しない。配備時はHTTPSを使用し、API認証はサーバー側で追加できる境界にする。
実メールの検証にはユーザーによる安全な認証情報設定が必要。チャットでは値を要求しない。

## 取得と重複排除
初回は指定日から取得し、その後はメールボックスのUIDVALIDITYとUIDカーソルを永続化して新着を処理する。
IMAP UIDはアカウント・メールボックス・UIDVALIDITYと組み合わせて識別し、裸のUIDを全メール共通の一意キーにしない。
Message-IDを第一の重複キーとし、欠落時は正規化した件名・日時・本文のハッシュを利用する。
VMGも同じ取込処理を使用し、経路に関係なく重複を防止する。既存VMG形式確認後に日時・本文の正規化を固定する。
メールと解析結果はトランザクションで保存する。解析失敗は記録し、カーソル進行によって失敗メールを再処理不能にしない。
件名または本文の店舗名・時間帯・稼働報告表記を正規化して判定し、送信元は環境変数で設定できるようにする。

## 解析とDB
全角・半角、空白、改行の揺れを正規化する。貸玉種別は数値＋円＋P/Sで認識し、新種別を固定リストなしで扱う。
日付、報告時刻、店舗、台数、男女・合計客数、稼働率、シェア、注目機種群を抽出する。
欠落値をゼロに置き換えない。明記された店舗総合と貸玉合計は区別し、算出値には由来を持たせる。
emails、store_summary、rate_summary、special_groupと同期状態テーブルを設ける。
メール識別子の一意制約、外部キー、日付・時刻・店舗・貸玉の検索インデックスを設定する。

## APIと同期
POST /api/sync、GET /api/status、GET /api/summary、GET /api/rates、GET /api/specialsを提供する。
from、to、time、store、rateを検証し、SQLはバインド変数を使用する。
同期状態は最終試行・最終成功・最新メール・新規件数・重複件数・最新データ日・秘密を含まないエラーを返す。
同期は排他制御し、失敗・未着を成功取込と区別する。
node-cronはAsia/Tokyoで毎日11:10、11:30、15:10、15:30、19:10、19:30に動作する。

## PWAと分析
既存画面、VMG読込、IndexedDB、CSV、各フィルタ、ランキング、推移、貸玉・店舗総合・注目機種群一覧を維持する。
メール同期ボタン、同期日時・件数・エラー、オンライン状態を追加する。
前日・前週・4週前・前月同日を同じ報告時刻と店舗で比較する。前月に同日が存在しない場合や比較データ欠落時は比較なしと表示する。
客数差と稼働率・シェアのポイント差を区別する。
取得済み集計をIndexedDBへ保存し、オフラインでは「最終取得データを表示中」と表示する。Service Workerで画面資材をキャッシュし、同期APIはキャッシュしない。
オンラインVMG取込は共通のバックエンド取込へ渡す。オフライン取込は既存の端末内保存を維持し、復帰時に保留メールを同じ取込処理へ送る。古いバックアップの解析済み行も保持し、レポートキーでサーバーデータと表示上の重複を除く。
既存コードにはsummaryタブがS.summaryを参照する一方、保存配列はS.summariesという不一致があり、初期表示・一覧・CSVで例外となる。統合時に参照を修正し、既存機能の回帰テスト対象にする。
既存Service WorkerはAPIもキャッシュする構成のため、APIを除外し、画面資材のみキャッシュする。日付比較はAsia/Tokyoの暦日で計算する。

## 検証と完成条件
解析は空白違い、新しい貸玉、11/15/19時、対象外メール、欠落項目をテストする。
同期は1通・複数・未着・接続失敗・再同期・VMGとの重複・UIDVALIDITY変更を模擬サーバーで検証する。
APIのフィルタ・入力検証、DB再起動後の保持、スマホ表示、オフライン起動と復帰を検証する。
実docomo IMAP接続は認証情報が安全に設定された後に別途検証し、模擬テストと区別して報告する。
READMEに起動、.env、docomo設定、手動／自動同期、HTTPS配備、PWAインストール、障害診断を記載する。

## 次に必要な入力
既存PWAのZIPは受領・確認済み。実装前にこの設計書の確認を行う。
実VMGや報告メールが提供可能な場合は個人情報を除いたサンプルで互換性を検証する。

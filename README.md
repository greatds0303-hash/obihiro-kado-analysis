# EAGLE 帯広店 稼働分析

既存PWAを維持し、docomoの稼働報告メールをバックエンドで取得するアプリです。本文貼付・VMG履歴の読込とIMAP同期を共通の解析・重複除外・SQLite保存に接続しました。Androidの縦画面、オフライン表示、CSV、JSONバックアップに対応します。

## スマホだけで使う手動版（既定）

**メールのID・パスワードも、メール取得用バックエンドも不要です。** 静的PWAをHTTPSで公開すれば、スマホだけで分析できます。

1. ドコモメールで稼働報告を開き、**本文全体をコピー**します。
2. アプリの「メール本文を取り込む」欄へ貼り付けます。
3. 「本文を取り込む」を押します。客数・稼働率・比較が更新され、この端末に保存されます。

同じ本文を再取込しても重複しません。過去のVMGもそのまま読み込めます。既定の手動モードではバックエンドAPIへ通信しません。

### GitHub Pagesでスマホ用のURLを作る

このリポジトリの`.github/workflows/pages.yml`は**手動実行だけ**の公開手順です。pushしただけでは公開しません。

1. GitHubのリポジトリ **Settings → Pages** で、Sourceを **GitHub Actions** に設定します。利用できるかはリポジトリの公開範囲・契約によります。
2. **Actions → Publish manual PWA → Run workflow** を開き、`feature/docomo-imap-sync`を選んで実行します。
3. 成功後にPagesに表示されるHTTPS URLをAndroidのChromeで開き、ホーム画面へ追加します。

公開するのは`public/`の画面資材だけです。.env、SQLite、メール本文、端末内の分析データは公開対象に含みません。公開ワークフローは準備済みですが、この作業では実行していません。

`public/`を別の静的HTTPSホスティングへ置く方法でも利用できます。提供する手動版ZIPには画面資材だけを含めます。ZIPを解凍して直接ファイルを開く方法ではPWAにならないため、HTTPS配信が必要です。

## 起動

Node.js **24以上**が必要です。

```sh
npm ci
cp .env.example .env
chmod 600 .env
npm start
```

開発用サーバーはポート3000で起動します。既定では同じPCからのみ接続できます。まずブラウザでサーバーのルートを開き、本文を貼り付けるかVMGを読み込みます。自動取得を使う場合だけ「自動同期を使う場合の設定」でサーバー連携へ切り替えます。IMAP未設定でもVMGの読込・分析は使えます。

`.env`はバックエンドだけに置き、GitHubへ保存しないでください。`.env`の内容をチャットや画面のログイン欄へ貼り付けないでください。

## docomoメールの設定

docomoメールの他端末利用・IMAP利用を有効にし、**IMAP専用ID・専用パスワード**を取得してください。dアカウントの通常パスワードを代用しないでください。契約や設定により利用条件が異なるため、[docomo公式案内](https://www.docomo.ne.jp/service/docomo_mail/other/)を確認してください。

サーバーの`.env`に以下を設定します。実際の値はここでは示していません。

| 変数 | 用途・既定値 |
| --- | --- |
| `DOCOMO_IMAP_HOST` | `imap.spmode.ne.jp` |
| `DOCOMO_IMAP_PORT` | `993`、TLS証明書検証を維持 |
| `DOCOMO_IMAP_USER` | IMAP専用ID |
| `DOCOMO_IMAP_PASSWORD` | IMAP専用パスワード |
| `DOCOMO_IMAP_MAILBOX` | `INBOX` |
| `REPORT_SENDER` | `square_obihiro@eaglegroup.co.jp`。空欄なら送信元制限なし |
| `IMAP_SINCE` | 初回取得の開始日、既定 `2026-01-01` |
| `ENABLE_CRON` | `true`。`false`で定時同期を停止 |
| `DB_PATH` | `data/kado.sqlite`。公開ディレクトリ外に置く |
| `HOST` | `127.0.0.1`。外部配信時はネットワーク構成に合わせて変更 |
| `PORT` | `3000` |
| `NODE_ENV` | 開発は `development`、HTTPS配備時は `production` |
| `APP_PASSWORD` | アプリ用のログインパスワード。本番は16文字以上を必須化 |

設定変更後はバックエンドを再起動します。認証情報をフロント・IndexedDB・localStorageに保存することはありません。アプリのログインは別の`APP_PASSWORD`で、8時間のHttpOnly／SameSite Cookieを使います。バックエンド再起動後は再ログインします。

## 取込と同期

- **VMG履歴**：ファイルを複数選択できます。UTF-8／Shift_JISのbase64本文を解析します。1ファイル20MBまで。オンラインではサーバーへ登録し、オフラインでは端末内に保存して通信復帰後に送ります。
- **新着メール**：「メール同期」で前回処理済みUID以降を取得します。バックエンド起動時にも設定済みなら同期します。
- **過去メール**：「過去メールの取得」で開始日を指定して同期します。1回最大500通を読み、残りがある場合は開始日欄を空にして再度同期します。古い日付へ遡るときは再び開始日を指定します。指定開始日は失敗時も保持し、次の通常同期で再試行します。
- **手動本文**：本文欄へ貼り付けて取り込みます。手動モードでは端末内だけで動作し、サーバー連携へ切り替えた場合は保存済み本文をサーバーにも登録します。
- **自動同期**：バックエンドが常時稼働している間、日本時間の毎日 **11:10・11:30・15:10・15:30・19:10・19:30** に確認します。メール未着でも次回再確認します。画面は表示中に毎分、取得済みデータを更新します。
- **重複**：Message-ID、メールボックス・UIDVALIDITY込みのUID、正規化本文のSHA-256を使用します。Message-IDがない場合もVMGとIMAPの同本文を重複登録しません。
- **大きなメール**：送信元が対象外のメールは本文を取得しません。10MBを超える候補メールは同期を止めず未取込として警告を残します。必要な報告は本文を手動取込してください。
- **解析失敗**：既に保存されたメールは残し、失敗した位置を越えてカーソルを進めません。本文形式を確認後、再同期できます。

対象判定は件名／本文の店舗名と稼働報告表記、または本文の日付・報告時刻で行います。IMAPの送信元制限は`REPORT_SENDER`で変更できます。VMGは履歴互換性のため送信元を必須にしません。

## 分析とオフライン

最新11時客数、11・15・19時比較、前日・前週・4週前・前月同日比較、貸玉別の客数差と稼働率／シェアのポイント差、店舗ランキング・推移・各一覧を表示します。比較元がない場合は「比較なし」。前月に同日がない31日なども比較なしです。総合計が本文にない場合は貸玉客数を合算し、総台数から稼働率を算出します。客数シェアは推測しません。

初回にオンラインでアプリを開くと、画面資材と取得済みデータを端末内に保存します。その後はオフライン起動でき、「最終取得データを表示中」と表示します。メール同期はネットワーク復帰後に利用できます。

従来版と同じIndexedDB名・保存キーを使用します。ただし**配信先のオリジンが変わる場合、ブラウザの保存データは共有されません**。旧版の「バックアップ」からJSONを保存し、新版の「復元」で読み込んでください。復元した古いJSON履歴は端末内に保持されます。未送信のVMG・貼付本文も新しいバックアップへ含めます。サーバーにも履歴を共有したい場合は、元のVMGを読み込んでください。

「データクリア」はこの端末の保存データと未送信VMGを消します。サーバーのDBは消しません。オンライン更新でサーバーデータが再表示されることがあります。

## スマホへのインストールと本番配備

手動版のスマホインストールは上記のGitHub Pages等のHTTPS配信だけで利用できます。以下は**自動同期を使用する場合のみ**の配備手順です。常時稼働するNode.jsサーバーと同じオリジンのHTTPS配信が必要で、GitHub PagesだけではIMAP取得・SQLite・cronは動作しません。

1. サーバー側にリポジトリとNode.js 24以上を用意し、`npm ci`を実行します。
2. `.env`にIMAP情報と十分長い`APP_PASSWORD`、`NODE_ENV=production`を設定します。
3. HTTPSリバースプロキシから同一オリジンで画面と`/api`を配信します。プロキシのHostヘッダーは外部公開ホストと一致させます。通信のタイムアウトは90秒以上に設定してください。
4. `npm start`をサービス管理機構で常時稼働させ、DBを永続ディスクに置きます。**1つのDBにつき1プロセス**で運用してください。
5. AndroidのChromeでHTTPSの公開URLを開き、アプリ用パスワードでログインします。「アプリをインストール」または「ホーム画面に追加」を選びます。

IMAPへのDNS解決とTLS/TCP **993番**の外向き接続が必要です。HTTPS専用プロキシの秘密置換はIMAP認証の代わりになりません。TCP接続とサーバー側認証情報を安全に提供できる配備先を使用してください。

## API

| API | 動作 |
| --- | --- |
| `POST /api/session` | `{password}`でログイン |
| `DELETE /api/session` | セッション終了 |
| `POST /api/sync` | 新着同期。任意の `{since:"YYYY-MM-DD"}`で再取得 |
| `GET /api/status` | 最終試行／成功、最新メール、件数、最新データ日、エラー、設定有無 |
| `GET /api/summary` | 店舗総合 |
| `GET /api/rates` | 貸玉別 |
| `GET /api/specials` | 注目機種群 |
| `GET /api/data` | PWA形式の全データ |
| `POST /api/import/email` | `{text}`で貼付本文を登録 |
| `POST /api/import/vmg` | `application/octet-stream`のVMGを登録 |

集計APIは`from`、`to`、`time`（11/15/19）、`store`、`rate`に対応します。認証設定時はセッションCookieが必要です。CORSは開放せず、別オリジンの更新要求は拒否します。APIはキャッシュしません。

## テストと障害確認

```sh
npm test
npm run test:e2e
```

ブラウザ検証は環境にChromiumがあれば使用します。別の実行ファイルは`CHROMIUM_PATH`で指定できます。Chromiumがない環境では`npx playwright install chromium`が必要です。

[検証結果と制限](docs/testing.md)を参照してください。実docomo接続は専用ID・パスワードとTCP接続が用意された後に検証が必要です。

同期エラーは画面または認証済み`GET /api/status`で確認します。IMAP未設定ならサーバーの変数名・設定有無、接続失敗ならDNS・993番の到達性・docomo設定を確認します。解析失敗なら日付・店舗・総合／貸玉の本文形式を確認し、個人情報を除いたサンプルで解析テストを追加してください。パスワードをログへ出さないでください。

競合推移グラフでは全店舗の客数・稼働率を同時表示します。店舗チェックで表示を切り替え、貸玉で種別を絞れます。12.5円Sと20円Sは画面の「20スロ」カテゴリーに含めます（原文の貸玉名は保持）。時間「すべて」のグラフは11時を表示します。欠測の稼働率はゼロにせず、線を途切れさせます。
